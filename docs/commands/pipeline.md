# cfo pipeline

`cfo pipeline config-drift \| config-apply \| migrate <id> \| run <id> [--branch <b>] --intent-file <file> \| respond <id> [--branch <b> \| --run <run>] --action <fix\|approve> [--findings <ids>] [--instructions <text>] [--accept <ids>] [--reason <text>] \| recover <id> [--branch <b> \| --run <run>]`

Drive a gated task under its frozen policy: report or apply the owned shared no-mistakes settings in an explicit idle window, whose refusal names the gate runs it waits for, explicitly migrate a task's frozen snapshot to the current policy the shared config already runs while preserving its class and repair cap, which never needs the daemon stopped, validate a bounded gate start under the version-specific contract, taking the run's intent from the file `--intent-file` names (a short one may be given with `--intent <text>`) and handing it to no-mistakes in a file, never on a command line, where Microsoft Defender detected a long intent as a lure and Windows refused the start, answer one parked gate with an explicit fix or a no-op approval, or recover eligible unpublished work without moving its local branch.
Each acts in the task's own worktree, or with `--branch` or `--run` in whichever of its worktrees, an extra one `cfo worktree add` recorded included, has that branch checked out; a run must be its branch's latest, and a branch or run none of the task's worktrees has is refused.
`--accept` with approve is the registered CFO's own decision to take exactly the open ask-user and auto-fix findings as they stand, recorded in the task's status log; a goblin is refused.
`--reason` with approve is the reason an approved Test exception keeps, handed to the native engine's own `--reason` and recorded in the task's status log; it is the registered CFO's alone, a goblin is refused, and a reason on any other gate, with a fix, or blank or of more than one line is refused, so no approval is ever inferred from one.
Under policy version 6 `run` starts the gate on the task's own harness, with that task's model and effort, as a launch selection no-mistakes proves before any agent starts, prints it on a `pipeline gate agent:` line, and names a second harness only when the operator named it as the policy's fallback and it is signed in.
A live run of the same branch, head and intent is reattached to when its bounded hold ends with no decision, so repeating the command starts no new run and resets no review budget, and none of a new start's checks, such as origin's tracking ref, stops it, while a start of other work is still refused.
Mode eligibility follows [Task classes](../pipeline.md#task-classes).
Never auto-approves and never skips a step; exit 3 means unresolved work needs your decision.
