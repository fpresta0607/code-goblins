# goblins dev-drive

`goblins dev-drive [setup \| move --to <folder>]`

Say whether the home's worktrees, scratch and package caches are on a Windows Dev Drive, whether this machine has one or can have one, and why not, with each fixed drive's file system and trust.
For a Dev Drive that lives in a file, such as the `C:\DevDrives\CodeGoblins.vhdx` Code Goblins makes, a `file:` line under it names the file, which Windows tells any process through the drive's storage dependency, and how much of its drive the file takes, such as `file: C:\DevDrives\CodeGoblins.vhdx holds 14.2 GB of C:, and stays that size when goblins free space on D:`, since a dynamically expanding file grows as the drive fills and never shrinks by itself.
Windows tells that size only to a process that may open the file, and Code Goblins leaves its folder to administrators and Windows alone, so in any other process the line says how much could not be read because only a process run as administrator may read it, and it never guesses.
A Dev Drive is a drive Windows 11 formats for developer work: Microsoft Defender keeps scanning it, in performance mode, so opening a file no longer waits for the scan; it is not a Defender exclusion, and nothing in Code Goblins adds one or changes a Defender setting.
It is optional, and a machine that cannot have one (Windows older than 11 build 22621.2338, Defender's real-time protection off, or under 100 GB free on the system drive for a new one) keeps working exactly as it always has.
`move --to <folder>` checks the folder is on a Dev Drive Windows does not distrust, makes `worktrees`, `scratch` and `caches` there, proves it can write, and records the folder and the time in the home's `config\dev-drive.json`: from then on new goblins' worktrees, scratch folders and cache variables point there, while `state`, `data`, `config` and `bin` stay in the home.
None of the home's work is copied: a goblin already started keeps the folders its record names until it ends, and the janitor removes the home's old package caches once no goblin terminal started before the move runs.
Run again with the same folder it changes nothing; a second move elsewhere is refused.

Then it carries the gate's home, where no-mistakes keeps its database, the repositories it gates and a full checkout for each run, into `no-mistakes` in the folder, so every gate checkout lands on the Dev Drive too.
The gate's home moves whole and `NM_HOME` at user scope names it, never a junction at the old path: Go's `filepath.EvalSymlinks` fails below any directory junction, on the same volume or another, which broke the gate's test preparation when the gate's home was linked into the Dev Drive by hand (no-mistakes #172).
It waits, up to half an hour, until no gate run is in flight and `no-mistakes daemon uninstall` stops the daemon by its own consent, never a forced stop, then holds the daemon's lock so none starts while it works.
It copies the home, less the daemon's `socket`, `daemon.pid` and `daemon.lock`, and proves every copied file holds the same bytes by SHA-256.
In the copy alone it points every text value of the database that names the old home at the new one, in any table and any spelling, and proves none is left; then `config.yaml` and each gated repository's `core.hooksPath`.
It sets `NM_HOME`, points each gated checkout's `no-mistakes` remote at its moved repository, and starts the daemon on the new home, which installs its sign-in task there; no gate run was in flight, so the daemon has none to recover.
Only once the daemon runs there does the old home go, its links removed as links; until then the old home is untouched and is the backup.
A step that fails, or an interrupt such as Ctrl+C, undoes every step before it, the copy included, and starts the daemon on the old home again; a move ended outright, its terminal closed among other ways, leaves a marker beside its copy, and the next move replaces that copy.
A gate home already in the Dev Drive folder changes nothing, and a gate home not made yet is named there from the start.
A gate home a move by hand linked into the folder with junctions is recognised: the folders its junctions lead to stay where they are, and what else that move copied into the folder, which the old home holds newer, is set aside while the move runs and removed once it is done.
A gate home that is itself one junction to `no-mistakes` in the folder is carried in place, with nothing copied: its records are pointed at the folder and the junction is removed as a link once the daemon runs there, and the folder is read again for the database and every gated repository it held before the move reports done.
Links inside the gate's home, such as those pnpm and Next.js leave in a run's checkout, are made again as their own kind, a junction as a junction and a symbolic link as a symbolic link: one leading inside the home is pointed at the new home, one leading outside keeps its target, a relative one stays relative, and each is read back before the move is done.
The move never walks into a link, and the old home, or a failed move's copy, is removed with each link removed as a link first, so what a link leads to outside the home is never touched.
A gate home that is itself a junction to any other folder, or holds a junction into `no-mistakes` in the folder that leads anywhere but its own place there, is refused by the move before the daemon is touched.
`goblins dev-drive` and `goblins doctor` name such a junction at the home's top levels, the home itself, its entries and theirs, instead of offering the move.
A move whose gate runs stay in flight the whole half hour changes nothing of the gate's home and exits 1, and the board offers the gate's home a step of its own, **Move the gate's home**, which runs this command again on **Try again**.
`goblins dev-drive` and `goblins doctor` say where the gate's home is (`gate home:`), and warn when the home's heavy folders are on a Dev Drive while it is not, or reaches the drive through junctions.
Every no-mistakes the fleet starts is given `NM_HOME`, so a board or terminal started before the move works in the moved home, and a goblin started after it gets the variable from Windows.
Once the gate's home is carried, a supervisor serving the home is restarted once on the build it runs, as `goblins update` restarts it, when the heavy folders moved now or the gate's home moved or was placed by this move, and never for a gate home already on the drive: it starts with `NM_HOME` naming the moved gate home, so what it starts itself builds on the drive and its gate reads the moved home, and every terminal keeps running.
The setup window and the board's first page each offer it once, unticked, where this machine can have one (`goblins install --dev-drive on|off` keeps the setup's answer; the first page keeps its own), and say in one line why where it cannot.
A person never types any of it: **Set up** under Dev Drive in the board's Workspace panel, or `setup` from a terminal, which the board notices within a minute, records `"choice": "wanted"` and the supervisor makes each step that needs him a Command Center item, one at a time, in order, each safe to run twice: create the drive (administrator: a dynamically expanding VHDX under `DevDrives` on the system drive, `Format-Volume -DevDrive`, and a startup task that attaches it at every boot), trust it only where Windows does not (administrator: `fsutil devdrv trust`, then `fsutil devdrv query`), and move (this command); an existing Dev Drive is used instead of a new one.
A step's item is made once for each ask, so one that failed or expired waits for **Try again**; a drive that is missing gets an **Attach** item by itself, at most every 12 hours
