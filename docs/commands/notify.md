# goblins notify

`goblins notify <id> --done --pr <url> [--lesson "<one line>" --cites "<stamp or words of a status line>"]... \| --done --closed <issue-url> --decision <sequence> \| --done --report <file> \| --blocked "<question>" \| --failed "<reason>" \| --working "<what>" \| --prepared-wait task:<id>\|pr:<URL> --generation <generation> --handoff <handoff-file> \| --waiting-on <task-id\|run-id\|overlord\|ci\|deploy\|memory\|gate-daemon\|docker> "<why>" [--lavish <html-file>] [--link <https-url>] [--run <command-file>] [--follows <question-id> \| --separate] [--message-file <file>]`

A goblin reports its outcome (PR URL, blocked question, or failure reason) straight into the wake queue, waking the CEO with the real payload instead of the watcher guessing from pane text.
A `--done` or `--failed` report also names, in its line and its wake, what the goblin started that still runs beside the report's own tool call, a machine service aside, as the supervisor's start watch places it, and tells the goblin to end what it no longer needs by its pid.
The tool call's own is never named: the report and what runs under it, every process attached to the console of the shell it was sent from, that console's host, and every process those run under.
So neither that shell, nor the console host Windows starts beside its hidden console, nor a program of the report's pipeline such as `tail` is named, though Git Bash starts such a program, or a `timeout` the report runs under, by replacing its own Windows process, which leaves it no parent.
A program the tool call started with a console of its own is named, and one it started in the background on its own console is left to the start watch's `left_running` wake, which names it once the goblin has rested a minute with it still running.
Where a harness runs its tool calls in its terminal's own console, which everything the goblin started there shares, the console counts for nothing, and only the report, what runs under it and what it runs under are left out.
What a report would name it reads again two seconds later, and it names only what still runs then by its pid and its start, so a tool call run beside the report that ends meanwhile is not named. **`--done` is per delivery, not per task: `--pr` records the literal line `done: PR <url>`, `--closed` and `--report` the lines below, and a task can ship several under one id, which is the ordinary shape for a landing task.** So a terminal verb in a status log establishes that a delivery finished and nothing whatever about whether the goblin is still working; anything that reads it as "the goblin is gone" is wrong, and the more destructive the thing it decides, the more wrong.
Live evidence answers that question: a pane holding an agent working in the goblin's worktree.
A task ruled finished with no pull request, such as one whose issue closes as no defect, a duplicate or already fixed, reports `--done --closed <issue-url> --decision <sequence>` in place of `--pr`, once it closed the issue.
`--closed` takes the link of a GitHub issue, and `--decision` the wake sequence of the goblin's own question in its current run, or that question's ID.
That question's `--blocked` notify prints its sequence, since only an answer from `goblins answer` names it, and one the Overlord gives on the board does not.
The notify reads that question's answer from its record and records `done: closed <issue-url> (decision <sequence>: <answer>)`, so the report quotes what was decided rather than the goblin's account of it.
The record proves an answer was given, and only its words say it approved this, which is why the line carries them.
A question the goblin never asked, one from an earlier run, one with no answer on record and a `--done` with none of `--pr`, `--closed` and `--report` are refused before anything is recorded, and so is `--closed` from a helper, whose done needs neither.
So the goblin asks with `--blocked` and choices, which the CEO answers with `goblins answer` or the Overlord on the board: a `goblins send` leaves no decision on record.
The same issue reported again wakes nobody, as a pull request's unchanged head does.
Nothing asks GitHub whether the issue closed, since a goblin's terminal may carry no credential to ask with: the link is there for the CEO to follow.
Cleanup, the board, a restart, the wake for its gone terminal and the AFK report all read that line as a delivery.
A task spawned local-only opens no pull request, such as a scout or an operations task with no commit, so it reports `--done --report <file>` in place of `--pr`, naming the file of its report.
The report must be a non-empty file, and the notify keeps it where cleanup reads it, as `data/<id>/report.md` in the home, unless it is that file already.
It records `done: report <path>` with the full path of that kept report, which cleanup reads as the task's delivery once the report is there.
The board, a restart, the wake for its gone terminal and the AFK report read that line as a delivery too, as they read a closed issue's.
A different report the home already keeps for the task is never replaced: the notify is refused, and the goblin names that report or writes its own there.
`--report` beside `--pr`, `--closed` or `--decision`, from a helper, whose done needs none, and from a task spawned no-mistakes or direct-PR, which reports its pull request, is refused before anything is recorded, and so is a report that is missing, empty or not a file.
A refused notify keeps no report, so the home keeps one only beside its done line.
The same report reported again wakes nobody, as the same closed issue does; a report with different content wakes the CEO again.
The first instruction of a task spawned local-only names this done and asks for no pipeline run and no pull request.
A done report may carry up to three lessons the next goblin in its repository should know, each a `--lesson "<one plain line>"` followed by a `--cites` for every status line of the task it stands on, given as that line's stamp or as words the line holds, the latest such line counting.
A fourth lesson, a lesson that spans lines, holds a control character or cites nothing, a cite no status line of the task matches, a `--cites` before any `--lesson` and a lesson on any report but a done are refused before anything is recorded.
The lessons never join the done line: each is recorded under `state/lessons` as a candidate with the status lines it cites, and the report prints their ids.
`goblins drain` lists each candidate on one line until the CEO accepts or rejects it with [`goblins memory lesson`](memory.md).
A question goes out as `goblins notify <id> --blocked "<one short question> options: <answer> (Recommended) \| <answer>"`: the question in one short sentence, every detail on a line of its own that starts with `- ` and comes before `options:`, and the choices after `options:` on its line, each the answer itself as a short phrase, such as `Fix it next` or `Keep 300 s`.
Its `- ` lines give the recommendation and what each choice does in plain words, and run IDs, finding codes and other evidence go after a line that reads only `Details:`, which the Command Center folds under Technical details, as the [decisions procedure](../contract/decisions.md#user-decisions-on-the-board) shows.
`goblins drain` shows it as a decision with those choices listed.
A detail on a line after the choices is recorded before them, so it never joins a choice.
A question that writes `options:` more than once, has fewer than two choices after it on its line, or offers a choice that is only a letter or number is refused before anything is recorded, with how to ask.
The same question sent again while it still waits unanswered is the same decision: the goblin is told, and the CEO is not woken again.
`--working` and `--waiting-on` are status for the board: they wake nobody and replace a stale blocked or failed reading, except that waiting on the Overlord wakes the CEO and puts an item in the Command Center, which a later `--blocked` question does not replace (the goblin waits on both, so it never files the wait again), and a wait on the CEO (`--waiting-on ceo`) or on a backlog row of kind `goblins` wakes the CEO once it has lasted 10 minutes ([Supervision](../contract/supervision.md#supervision)); a wait on another task clears itself when that task reports done, and the CEO releases any wait with `goblins notify <id> --working "<what>"`.
Since they wake nobody, a `--working` report or a wait on anything but the Overlord that asks a question with choices (choices after `options:` in any case, a choice marked (Recommended), or choices split by `|` after a question mark) is refused before anything is recorded and told to go as `--blocked`, so the question reaches the CEO as a decision and the board reads the goblin as blocked.
`--prepared-wait task:<id>` or `--prepared-wait pr:<GitHub PR URL>`, with `--generation <generation>` and `--handoff <handoff-file>` and no other flag or argument, says the goblin's preparation is complete and no worker-owned work remains while it waits for that task to deliver or that pull request to merge, and authorizes one automatic dependency pause.
`--generation` is the terminal's current spawn generation, as `GOBLINS_SPAWN_GEN` holds it, and `--handoff` is the handoff the goblin saved as `data/<id>/handoff.md` in the home.
The notify proves it runs in the task's own native terminal, as a question does, rather than trusting an inherited task or generation variable.
It refuses before recording anything a generation that is not that terminal's current one, a conversation not saved for that generation, a handoff that is not the task's saved one or is empty or larger than 1 MiB, a worktree with uncommitted or untracked changes, a head on no branch, and a task target that is the goblin's own.
Its record, `state/prepared-waits/<id>.json`, binds the generation, project, worktree, saved session, branch, head, the handoff's path and SHA-256 digest and the condition under one stable operation id, and the status log gains `waiting on <target>: preparation complete; no worker-owned work remains (<operation id>)`, which the board reads as a wait.
The identical signal sent again records nothing and renews nothing.
Another task's delivery and a pull request's merge are the only conditions it takes; a feature's installation is not one.
A plain `--waiting-on` keeps its meaning as status for the board and never authorizes a pause or a stop, whatever its words say of the wait.
What the supervisor checks before it pauses the goblin, and how it resumes it, is in [Pausing and automatic resume](../contract/dispatch.md#pausing-and-automatic-resume).
A wait on the Overlord while a step card the goblin filed itself is open is that card, as a wait with `--run` is its run card: no second item opens, the notify names the card and tells the goblin to wait on it in the background with `goblins auth request --wait-on <card> --task <id>`, which ends when the card closes, and the board reads the goblin as waiting until it reports again, as for a run card.
Done on the card, or its inputs arriving, also closes a wait the goblin opened while it was open.
A wait on the Overlord that needs his answer on a Scrawl page names it with `--lavish <html-file>`: the notify opens the page without a browser and refuses, recording nothing, when it cannot; the page's link goes into the wait's line and onto its Command Center item, and the supervisor polls the page, so his feedback there reaches the CEO as a `review` wake with the whole reply saved under `state/reviews/feedback/`, and the item closes.
While AFK mode is on the same wait is instead that goblin's question to the CEO, which answers it with `goblins answer` in his place ([AFK mode](../contract/afk.md#afk-mode)).
A goblin never runs `lavish-axi poll` itself: that poll takes his feedback where only the goblin sees it.
`--waiting-on overlord` is only for a wait on the Overlord personally: his sign-in, his click, his page.
Such a wait is a card in his Command Center only when it names what he acts on: `--lavish`, `--link`, `--run`, a step card or file the goblin filed, or a decision it `--follows`; one that names none wakes you with ` (no card: it names nothing he acts on)` on its line and opens no card, so put the step to him yourself as a card that acts (`goblins run-request`, `goblins question`) or answer the goblin.
Lead such a wait with one sentence; values he must enter somewhere go in a Markdown table on the lines after it, each value in backticks so his card copies it with one click (the notify help shows the form), and the one place he goes is `--link <https-url>`, the only link his card opens.
A command he must run himself, such as a sign-in, goes in a `.ps1` or `.sh` file named with `--run <file>` on the wait or the question: his Command Center shows it on a run card named for the goblin and runs it with one click in a terminal on his card, where he types into it, and the goblin is told how it ended.
A `--blocked` question with choices, or a `--run` command, carries a message he sends himself, such as an email, with `--message-file <file>` in the form `goblins auth request` takes: the question's card shows it when it offers choices, the run card otherwise, and a report no card shows, such as a helper's question to its parent, refuses it before anything is recorded.
A choice the CEO can make, such as whether a goblin starts something now or after a reset, is an actual question and uses `--blocked` with options, so it reaches the CEO rather than sitting in the Overlord's Command Center as a wait.
While a decision for the goblin is open, its own `--blocked` question with choices or your `goblins question --for <its id>`, a `--waiting-on overlord` declares what it is: `--follows <question-id>` when the wait is that decision, which is then hidden while the decision is open and closed by its answer, so he sees one card, or `--separate` when it is a card of its own, as a wait with `--lavish`, `--link` or `--run` always is.
A wait that declares neither is refused before anything is recorded, naming each open decision by its question ID and first line, and so is a `--follows` that names no open decision; nothing guesses which a wait is, since a need he never sees stalls the goblin and an extra card does not.
With no decision open a wait needs neither flag.
